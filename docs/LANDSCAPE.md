# Landscape: process-capture tools and what they claim

AgentCaptureBench evaluates tools that record process execution. This document summarizes — at the level of each project's own public documentation — what the main tools in this space set out to capture, so that benchmark results can be read against *stated* guarantees rather than vibes.

Two rules govern this document:

1. **A tool is only ever scored against its own documented guarantee.** Missing an event the tool never claimed to capture is a *scope limitation*, not a capture failure (see the classification discipline in the [README](../README.md#classification-discipline)).
2. **This is a living document.** If a description below misstates a project's scope, a correction PR with a link to the project's documentation is welcome and will be merged quickly.

## Categories

Capture tools differ first in *where* they observe:

- **Kernel audit subsystems** (auditd) — the kernel's own audit framework; execve records are generated by audit rules.
- **eBPF-based tracers and sensors** (execsnoop, Tetragon, Falco, Sysdig) — programs attached to tracepoints/kprobes that stream execution events to userspace.
- **Host telemetry agents** (osquery) — scheduled or evented queries over OS state and event tables.
- **Deterministic recorders** (rr and research systems) — record execution for faithful replay, a stronger claim than event logging.
- **Agent/application-layer recorders** (DEPOSE, Tracekit, and similar) — record what an AI agent or application *did* at the framework/API level; whether OS-level child processes are in scope depends on the tool.

The interesting benchmark questions live at the seams: a hook-level recorder and a kernel-level recorder can both be "complete" relative to their scope while disagreeing about the same run — which is exactly what the oracle comparison exposes.

## Tools

### auditd (Linux Audit Framework)

- **Observation point:** kernel audit subsystem; `execve` audit records emitted when audit rules are configured for the syscall.
- **Stated scope:** system-call auditing per configured rules — capturing execve depends on rules being present and the audit daemon keeping up; under load, events can be dropped when the backlog limit is reached, which the framework surfaces as lost-event counters.
- **What the benchmark tests:** whether a correctly configured auditd records all six scenario cases (including the Python-launched `git`), and whether drops under stress are detectable from its own accounting rather than silent.

### BCC / bpftrace `execsnoop`

- **Observation point:** eBPF attached to execve tracepoints; prints each successful exec with argv as it happens.
- **Stated scope:** a tracing/observability script, not a guaranteed-completeness recorder — events can be lost when the perf buffer cannot drain fast enough, and very short-lived processes are a known hard case for exec tracers generally.
- **What the benchmark tests:** baseline sanity — execsnoop shares the oracle's observation family, so discrepancies between it and the oracle isolate buffering/processing loss from observation-point differences.

### Tetragon (Cilium)

- **Observation point:** eBPF sensors with in-kernel filtering and aggregation; process lifecycle events (`process_exec` / `process_exit`) are a core event type.
- **Stated scope:** runtime security observability — process execution events with parent information and (policy-dependent) argument capture, designed to be low-overhead and production-safe.
- **What the benchmark tests:** exec coverage for all six cases under a default tracing policy, accuracy of parent/child correlation for the pipeline and interpreter-child cases, and behavior on the nonzero-exit case.

### Falco

- **Observation point:** kernel module or eBPF probe feeding a rules engine over syscall events, including `execve`.
- **Stated scope:** runtime threat *detection* — Falco's contract is alerting on rule matches, not producing a complete execution log. Scoring Falco on raw capture completeness without accounting for that scope would be a category error; adapters must map its output to the events its rules are configured to surface.
- **What the benchmark tests:** with an exec-logging rule configured, whether the surfaced events cover the scenario cases; without one, its entries are recorded as scope limitations by design.

### Sysdig

- **Observation point:** kernel module or eBPF probe capturing the full syscall stream to userspace (live or to capture files).
- **Stated scope:** deep syscall-level visibility — `execve` enter/exit events with arguments are part of the captured stream, subject to userspace consumption keeping up.
- **What the benchmark tests:** completeness of the execve stream across the six cases and fidelity of argv reconstruction versus the oracle's bounded argv.

### osquery

- **Observation point:** host agent; on Linux, process *events* come via its events framework (backed by audit or BPF publishers depending on configuration), distinct from point-in-time `processes` table snapshots.
- **Stated scope:** endpoint visibility through SQL tables — event completeness depends on the publisher, configuration, and query schedule; snapshots are not an execution log and are out of scope for capture scoring.
- **What the benchmark tests:** with the BPF/audit process-events publisher enabled, coverage of the scenario cases in `process_events`; the snapshot tables are recorded as scope limitations for execution capture.

### rr

- **Observation point:** ptrace-based deterministic record-and-replay of a recorded process tree.
- **Stated scope:** faithful replay of the *recorded* execution — a different and stronger claim than system-wide capture; processes outside the recorded tree are out of scope by design.
- **What the benchmark tests:** within a recorded run of the workflow, whether all in-tree execs (including the Python-launched `git`) are present and replayable; anything outside the tree is a scope limitation, not a failure.

### Agent-layer recorders (DEPOSE, Tracekit, and similar)

- **Observation point:** application/framework layer — agent lifecycle hooks, tool-call interception, or application instrumentation.
- **Stated scope:** varies by project and is often stated in terms of agent actions rather than OS processes. Whether OS-level child processes spawned by the agent are in scope must be taken from each project's documentation at adapter time, not assumed.
- **What the benchmark tests:** the central seam question — when an agent (or here, an interpreter standing in for one) launches a real child process, does the recorder's account include it, and if not, is that boundary explicit in its documented guarantee? Adapters for these systems are proposed through the [recorder adapter issue template](../.github/ISSUE_TEMPLATE/recorder_adapter.md).

## Summary table

| Tool | Observation point | Claims execution log? | Primary benchmark question |
|---|---|---|---|
| auditd | Kernel audit | Yes, per configured rules | Rule-configured coverage; are drops accounted? |
| execsnoop (BCC/bpftrace) | eBPF tracepoint | Observability, not a guarantee | Buffering loss vs. oracle on identical observation family |
| Tetragon | eBPF sensors | Yes, process lifecycle events | Coverage + ancestry correlation accuracy |
| Falco | eBPF/module + rules | Detection alerts, not a log | Only scored on events its rules surface |
| Sysdig | eBPF/module syscall stream | Yes, syscall level | Stream completeness + argv fidelity |
| osquery | Host agent (audit/BPF publishers) | Event tables, config-dependent | `process_events` coverage when enabled |
| rr | ptrace record/replay | Replay of recorded tree only | In-tree completeness; out-of-tree is scope |
| Agent-layer recorders | Framework hooks | Per project documentation | Do agent-spawned OS processes appear? |

## What AgentCaptureBench adds

None of the tools above ship with an independent check of their own completeness — each is its own only witness. AgentCaptureBench contributes the missing piece: a small, inspectable, kernel-level oracle, a deterministic workflow whose every step is independently accounted, and a classification discipline that refuses to blur the line between *the recorder missed it*, *the recorder never promised it*, and *we cannot tell yet*.
